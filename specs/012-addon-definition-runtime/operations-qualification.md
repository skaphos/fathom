Reproduction: prepare the archive/image and isolated Kind/core tier/Helm install as above, load current/prior/fixed local images, then run `qualification.sh phase1`, `phase2`, `phase3`, `phase5a`, `phase5b`, `phase4` with this file's `KUBECONFIG`. The script checks the context before every phase. Exact commands and assertions are in `qualification.sh`; logs and object snapshots are beside it. In the live execution phase 1's initial in-memory script did not yet save first-pass snapshots, so `first-pass-check.json` and `first-pass-report-names.json` were captured immediately after its successful run; the archived script now saves them. Phase 2's first scratch assertion mistakenly treated an omitted zero `activeRuns` as missing; it was interrupted, corrected to `(.status.activeRuns // 0)==0`, and resumed. These intermediate attempts are retained in their original log files.

The referenced `qualification.sh`, logs and snapshots live under `/tmp/fathom-downgrade-012/` and are local supporting artifacts, not committed repository inputs. This record preserves their exact environment, image identifiers and phase results so the bounded trial remains reviewable after the temporary Kind cluster is removed.

Observed invariants:

1. Default-off definition was inert while built-in CoreDNS passed. Runtime enable plus real dedicated-SA impersonation/read grants and exact definition/SA UIDs yielded Pass at `2026-09-22T16:26:49Z` on adapter version 1.0.0, one report (`first-pass-check.json`, `first-pass-report-names.json`, `phase1.log`). A valid same-verdict revision 1.0.1 yielded new evidence at `16:27:17Z` with exactly the same report name (`second-pass-check.json`, `second-pass-report-names.json`).
2. Binding disabled at generation 2 reached `Ready=False/AuthorizationRevoked`, `Drained=True`, `activeRuns=0` (omitted zero field), and a matching current leader epoch. Target CLI independently printed `Verified drained`; reader and impersonation grants were revoked. Complete JSON backups of all AddonChecks/status, HealthReports, definitions and bindings were written outside the cluster (`backup-*.json`, `backup-sha256.txt`, `drain-output.txt`). Backed-up Pass evidence retained `16:27:17Z` with `Unavailable` freshness.
3. Switching only the manager image/args to actual v0.5.1 retained new CRDs and data. After an ordinary runtime-only AddonCheck annotation, old `Status().Update` removed `lastSuccessfulEvaluation` and other new status fields (`old-binary-check.json`), while old CoreDNS built-in advanced and runtime report names did not change (`old-binary-peer.json`, `old-binary-report-names.json`, `phase2-retry.log`). This confirms HealthReport history alone cannot restore newest same-verdict evidence.
4. After the old Pod was gone, the current binary ran default-off. A JSON Patch to the AddonCheck `/status` subresource tested UID, generation and current resourceVersion before replacing status from the backup. Readback exactly matched the backed-up `lastSuccessfulEvaluation` including original observation time/revision/authority, with `Unavailable` freshness and identical report names (`restore-status-patch.json`, `restored-check.json`, `phase3.log`). After direct UID review, reviewed grants and runtime/binding re-enable, a fresh Pass at `16:32:06Z` under version 1.0.1 preserved the same report names (`revalidated-check.json`).
5. Under old v0.5.1, a stored `AddonDefinition coredns` plus exact-UID binding/grants did not stop compiled CoreDNS; the peer advanced and target CLI preflight returned collision exit 1 (`old-before-collision-peer.json`, `stored-collision-*.json`, `target-preflight-collision.txt`, `phase5a-retry.log`). The old Pod was then fully stopped before the fixed target image started. Fixed target startup reported `BuiltinCollision` and the peer's `lastRunTime` stayed at `16:39:19Z` through the blocked observation; explicit collision deletion recovered Pass at `16:41:24Z` (`fixed-startup-collision-peer.json`, `fixed-after-collision-peer.json`, `phase5b.log`). Both binaries already ship compiled CoreDNS: this tests a stored-name collision across binary versions, not a historically newly added builtin or the separate #256 ratio compatibility gate.
6. With isolated in-cluster Deployment scaled to zero, fresh host-local manager used explicit operator namespace, leader election, runtime opt-in and the dedicated kubeconfig but had no projected ServiceAccount token. It logged `AuthorizationUnavailable`, acquired the namespaced Lease, advanced built-in CoreDNS after run-now and left runtime evidence unchanged. The in-cluster Deployment was restored to 1/1 (`host-local-manager.log`, `host-local-peer.json`, `host-local-runtime-check.json`, `phase4-retry.log`).
